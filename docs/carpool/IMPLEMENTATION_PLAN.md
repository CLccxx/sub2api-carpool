**Goal:** 在 A 站完成邮箱注册登录、拼车收款登记和车辆管理；满员后管理员部署独立服务器 B；开通后成员仍在 A 管理 B 的 API Key 和本人用量，模型客户端直接调用 B。

**Tech Stack:** 沿用目标 sub2api 版本的 Go、Vue、PostgreSQL、Redis 和容器部署方式；增加节点控制面和持久化同步任务。首版不依赖新增身份服务或在线支付；现有 OIDC 能力保留兼容。所有付费资源与真实部署另行确认。

## 1. 已确认需求与范围

- 每辆车 2–4 个座位，展示已付款人数、可用座位、发起时间、当前状态。
- 用户通过付款确认成员资格；支付中的短暂占位与正式成员分别计数。
- 满员邮件通知管理员；第一版由管理员购买服务器并部署，不自动采购。
- 每辆车绑定一个独立服务节点和固定出口 IP。
- 用户只登录 A，不在每个节点重新注册、绑定或登录。
- 用户在 A 创建/管理对应节点的 API Key、获取每车独立 Base URL、查看本人节点用量；实际 Key 和用量由节点保存。
- fork 可持续合并上游更新，但每次需要兼容验证，不承诺无冲突升级。

第一版不做：自动购买服务器、统一跨节点 API Key、跨车余额钱包、自动跨节点故障转移、多个出口代理调度、复杂转座与自动补位。后台需保留受控退款和处理失败订单的能力。

默认业务规则：一名用户可参加不同车辆，但同一辆车最多占一个有效座位；服务周期从实际开通时间开始。价格、服务时长、招募截止时间、交付期限和退款规则必须在车辆发布前配置，不能上线后临时决定。

## 2. 目标部署

```text
A 服务器
  主站 sub2api + 拼车模块 + 统一用户控制台
  主站数据库与缓存
  加密的节点连接凭证与内部用户映射
  节点同步 worker（通知通道延期）

B 服务器：车 001
  sub2api + managed 节点权限及委托操作接口
  独立数据库、缓存、固定出口 IP
  该车专属上游账号

C 服务器：车 002
  与 B 同样的结构，数据和出口独立

用户浏览器 → A 网页和后端 → B 的管理 API
用户 API 客户端 → B → 上游
```

建议使用同一自有域名下的不同子域：主站、车 001、车 002。首版不要求独立身份服务子域。节点 DNS 直接指向对应服务器；第一版不让 A 或 CDN 代转模型请求。节点上的 TLS 终止组件可以与 sub2api 同机，但不要将其与跨服务器中转混淆。

一辆车的身份不依赖机器 IP：使用稳定 `car_id`，通过 `node_id` 关联部署目标。更换机器可保留车辆子域名，但 Key 能否保持不变取决于节点数据库和相关密钥是否完整迁移，单改 DNS 不够。

## 3. 身份与权限

### 3.1 主站身份与内部映射

A 沿用现有邮箱验证码注册和账号登录。主站生成稳定的实例编号及用户 subject，B 保存其与本地内部用户的唯一映射；不按相同邮箱或相同数字 ID 自动认领用户。节点成员预配不得产生默认余额/订阅，也不得创建管理员身份。

用户链路：

1. 用户登录 A，管理员核实站外收款后加入车辆，保持待部署。
2. A 后端在已验证的 B 建立内部用户映射，不复制任何登录密码，也不签发成员 B 会话。
3. 阶段 4 完成资源及全员准备并明确确认开通后，才发布带服务窗口的授权。
4. 用户在 A 操作该车密钥或用量页面；A 从本人身份计算 B 的用户范围，调用固定管理接口并过滤返回字段。
5. 用户模型客户端使用该车 API 地址和 Key，直接调用 B；B 检查本地成员资格及原有分组/额度规则。

既有 OIDC 模式作为兼容路径保留，并继续验证其安全性；它不再是新首版成员的前置条件。managed 与 oidc 显式互斥，不用伪造 OIDC 记录来适配内部用户，不共享各节点 JWT 密钥。

### 3.2 购买资格不等于登录身份

- A 保存订单和车辆成员关系，是购买资格的唯一权威来源。
- B 只接受发给本节点的成员授权：主体标识、车辆、有效期、状态、额度策略、版本号。
- 未授权身份默认拒绝使用；不能因为 OIDC 登录成功或自动建立了用户就获得默认赠送额度、公开分组或可用 Key。
- A 的成员入口和 B 的委托 Key/模型入口各自检查资格；managed 成员不直接登录 B 控制台。
- 管理员使用独立管理身份，车辆成员不能被同步为管理员。

### 3.3 节点同步与失效

A 首版使用各 B 自己生成的管理员 Key，经服务端固定接口调用复用节点管理能力；密钥加密存放，不交给普通用户浏览器。全局 Key 本身仍是广泛管理员权限，不因 A 的接口白名单而降权；专用限权凭证属于后续加固和上线评审。同步消息带版本、有效期和幂等标识，旧消息不能覆盖新撤销状态。节点地址受部署白名单、TLS、连接 IP 和节点身份验证约束，不接收用户指定的远端 URL。

阶段 3 的历史兼容路径采用 A 变更后下发、持久化失败重试及 A 每分钟对账，本地资格最多 15 分钟租约且不超过服务期限。阶段 4B 已针对完成原生初始化的车辆去除这项短租约依赖，由 B 原生订阅、用户/Key 状态及额度审核；A 不可用不额外停流。持久化变更同步仍保留，断网期间新的撤销必须送达 B 后才生效，不能承诺即时离线撤权。具体新链路证据见 4B/4D RESULTS，不把历史租约到期停流当作新目标。

新请求在本地检查服务到期时间；第一版已开始的流式请求允许完成，新请求拒绝。若业务要求立即中断在途流，应作为单独功能评审。API Key、订阅和余额等原有鉴权缓存也必须覆盖失效测试。

## 4. 核心数据与状态

以下是拟新增概念，不是声称上游已经存在的实体。

| 实体 | 关键数据与约束 |
|---|---|
| 车辆 `carpool_cars` | 容量 2–4、商品与价格快照、币种、周期、招募截止时间、状态、节点、实际开通时间 |
| 座位 `carpool_seats` | 车辆内固定序号；空闲/临时占位/已确认；占位到期时间；订单与成员引用 |
| 订单 `carpool_orders` | 本地订单号、用户、金额、支付渠道订单号、支付状态、退款状态；渠道交易号唯一 |
| 成员 `carpool_memberships` | 用户与车辆关联、服务有效期、开通状态；同车同人有效成员唯一 |
| 节点 `carpool_nodes` | 域名、固定出口信息、部署版本、健康状态、受保护的管理凭证引用 |
| 身份映射 | managed 模式的主站实例/稳定 subject 与节点内部用户 ID；旧 OIDC 映射保留兼容 |
| 事件与任务 | 支付去重、通知、成员下发、重试记录、管理员操作审计 |

车辆主状态：`招募中 → 已满员/待部署 → 部署中 → 服务中 → 已到期`。独立分支包括招募取消、部署失败和暂停服务。订单、退款、座位与车辆状态分别存储，不用一个状态字段混合表达。

锁位建议 10 分钟。数据库行锁/事务和唯一约束作为最终防超卖机制，Redis 只作辅助。占位到期任务与支付回调使用同一事务约束处理竞争。

支付回调验签后核对商户、订单、金额、币种和最终付款状态。重复事件只处理一次；本地座位已释放后才收到付款成功，进入异常付款/退款处理，不自动挤占他人座位。不得仅根据浏览器支付成功跳转页面确认上车。

满员与通知事件在同一数据库事务中写入，worker 异步发送，失败重试。通知按车辆和事件去重；邮件系统不保证绝对恰好一次投递，管理员后台的待部署列表才是可靠工作清单。

## 6. Fork 与代码组织

### 是否需要 fork

严格说不是技术上的必须：独立拼车站可以通过接口连接原版 sub2api。但本需求要嵌入 A 的导航、复用账户体验，并补节点授权，因此建议维护 fork。Fork 是维护自有改动的方式，不是多服务器部署的前提。

只维护一个 fork，不为 A、B、C 各建一套分叉。建议从同一代码基线构建镜像，通过拟新增的角色开关启用主站拼车模块或节点授权模块；这不是上游已经提供的配置。共享镜像不代表共享数据库、管理员账号或秘密。

### 缩小与上游的冲突面

- 拼车前端作为独立页面和组件，仅在路由、导航等少量位置接入。
- 拼车后端按 handler/service/repository 边界新增独立模块，沿用目标版本项目惯例。
- A 承担订单和成员权威数据；B 只增加身份关联、权限缓存和鉴权接入，避免把拼车状态塞进调度器。
- 使用带项目前缀的新表；评估目标迁移器后选用独立迁移目录与版本记录，禁止改写已执行的上游迁移或猜一个“大编号”永久避冲突。
- 原有支付能力可复用适配层，但业务履约必须明确区分拼车、充值、订阅。
- UI 不做全站重写；不做与拼车无关的批量格式化、重命名或数据库重构。
- 将通用修复或扩展钩子提交上游作为后续选择；不能把上游接受 PR 当作本项目上线前提。

## 7. 上游更新策略

建议的远程与分支约定：

```text
origin                 你的 fork
upstream               官方仓库
origin/main            尽量保持官方基线，不放业务改动
carpool/main           你的定制主分支
feature/<topic>        独立功能分支
upgrade/<version>      从 carpool/main 创建的上游合并测试分支
```

下面是之后的操作示例，不是本轮已经执行的命令。在工作区干净、远程配置和目标 tag 已核对后操作：

```bash
# upstream 仅在尚未配置时添加
git remote add upstream https://github.com/Wei-Shaw/sub2api.git
git fetch upstream --tags
git switch carpool/main
git switch -c upgrade/<目标版本>
git merge <已核实的上游发布标签或提交>
```

尖括号是需替换的 Git 参数示意，不应原样执行；目标版本必须取自实际仓库，不能根据版本号猜 tag 名。

升级流程：

1. 阅读上游发行说明及目标差异，重点检查 OIDC、鉴权、支付、数据库迁移和容器配置。
2. 在 `upgrade/` 分支合并目标上游版本，逐项解决冲突；不要用“全部采用 ours/theirs”掩盖业务变更。
3. 运行编译、原有测试、自有单元测试、节点接口契约测试和拼车端到端回归。
4. 使用脱敏的生产结构备份验证迁移，再构建自己的不可变版本镜像。
5. 为 A 与节点维护控制接口版本兼容窗口；新旧版本不兼容时安排协调升级，不直接混跑。
6. 备份数据库和部署配置，先升级测试节点，再按维护窗口升级单个试点节点，最后逐步发布。
7. 通过审核将升级分支合并回 `carpool/main`，记录上游 commit、自有 commit、镜像 digest 和迁移版本。

GitHub 的 Sync fork 功能可以更新指定分支的上游代码，但不等于帮定制分支验证兼容性，更不等于升级线上容器。同步代码、解决冲突、构建镜像、数据库迁移、部署是不同步骤。

升级时必须使用自己构建的镜像；不要把官方镜像或官方一键更新入口当作定制版更新方式。禁用或替换可能覆盖定制构建的自动更新机制。

回退需要同时评估应用与数据库：如果新迁移不向后兼容，仅切回旧镜像可能不能运行。优先设计可向后兼容的增量迁移；恢复数据库备份会影响备份之后的订单与使用数据，必须结合维护窗口、流水保存和恢复后支付对账处理，不能直接覆盖生产库。

## 8. 完成标准

- 用户只维护主站登录账号，节点内部映射只授予其已开通车辆的使用权限。
- 座位不超卖、付款不丢失、退款可追踪、邮件失败可以补偿。
- 手动部署后才开始服务计时；未授权完成的节点不被标成可用。
- 模型请求不经过 A 或额外远程出口代理。
- B/C/D 的数据库、Key 和出口独立；成员不能跨车越权。
- 到期和撤销影响实际 API 使用，不仅影响页面展示。
- 至少演练一次上游合并与定制镜像发布，以及数据库兼容检查和恢复方案。
