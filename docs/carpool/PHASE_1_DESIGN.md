日期：2026-09-16（Asia/Shanghai）

**状态：用户于 2026-09-16 确认，1A 与 1B 均已完成本地验收。任务级记录见对应 `PHASE_1A_PLAN.md`、`PHASE_1B_PLAN.md`，证据与边界见 `PHASE_1A_RESULTS.md`、`PHASE_1B_RESULTS.md`。不代表真实支付、生产交付或运营合规验收完成。**

## 1. 本阶段交付

主站 A 可以创建并发布 2–4 座车辆，用户浏览拼车大厅、领取临时座位、查看测试订单和“我的车”；测试夹具确认订单后产生待部署成员，全部座位确认后车辆进入“满员待部署”。

本阶段做到“可验证的招募与座位闭环”，不做到“付费服务上线”。不接真实支付/退款/SMTP，不采购服务器，不下发 B 节点授权，不更改模型转发路径。服务起止时间始终留空，界面不显示“已开通”或可用节点入口。

已确认规则沿用总方案：每车 2/3/4 座；同一用户同车最多一个有效座位，可参加不同车辆；占位建议 10 分钟；实际服务周期从部署和授权完成后开始，本阶段不启动计时。

## 2. 实现路线比较

| 路线 | 代价与风险 | 结论 |
| --- | --- | --- |
| 仅做页面与内存模拟数据 | 页面快，但不能验收数据库并发、重启、重复请求 | 不作为阶段 1 验收方案 |
| 独立拼车模块、PostgreSQL 事务、测试订单 | 少量新增表和路由，能直接验证座位不超卖；之后接真实支付适配 | **推荐** |
| 直接复用原充值订单履约，加入真实支付 | 原 `executeFulfillment` 对非订阅订单默认走余额履约，容易误充余额，且超出当前授权范围 | 暂不采用；阶段 2 再显式接入 |

保留现有 Go/Gin/PostgreSQL/Vue/Pinia、页面组件与 Wire 组织方式，不另建微服务或第二套前端。

## 3. 开关与模块边界

- 建议新增 `carpool_main.enabled`，默认 false；用户及管理 API、导航和页面均受服务端功能状态控制，不能只隐藏按钮。
- 测试订单另有 `carpool_main.test_orders_enabled`，默认 false。阶段 1 所有订单都带 `mode=test`，付款确认只能由本地测试 CLI 或集成测试夹具调用，不注册用户或公网确认接口。
- 主站模式与现有 `carpool_node.enabled` 互斥，误同时开启应拒绝启动，避免 B 提供主站业务入口。节点成员门禁逻辑不改。
- 继续使用 `backend/internal/carpool/` 作为独立领域边界：规则、SQL 存储、事务服务、测试夹具分文件；handler 仅做认证、DTO、参数校验和错误映射。
- 使用现有 `carpool_schema_migrations`，追加 `002_main_carpool.sql`，绝不改写已执行的 `001_node_memberships.sql`。主站启用时也调用迁移；共享二进制的节点可能创建空主站表，但不会复制 A 的订单或成员数据，也不注册主站路由。
- 不改上游调度器、支付履约、余额或订阅表。A 本地用户 ID 只用于 A 的所有权；跨站身份仍为已验证 issuer/subject，不能把 A 的 ID 下发成 B 的 ID。

## 4. 数据与不可变条件

表名、字段与接口是设计约定，实施计划阶段再给出精确 SQL 与 Go 类型。

| 表 | 主要字段与约束 |
| --- | --- |
| `carpool_cars` | 稳定文本 ID、名称、容量、单座价格、币种、服务天数、招募截止时间、满员后的交付时限、退款规则快照、状态、版本、创建/发布时间、满员时间；容量只能为 2/3/4 |
| `carpool_seats` | 车辆 ID、固定序号、状态、当前用户 ID、当前订单 ID、占位截止时间；`(car_id, seat_no)` 唯一；同车非空闲座位的 user_id 部分唯一索引；序号在该车容量范围内 |
| `carpool_orders` | ID、car/user/seat 引用、`mode=test`、价格/币种/规则快照、pending/confirmed/expired/cancelled、占位截止时间、请求幂等键与请求摘要、确认时间；同用户同操作幂等键唯一 |
| `carpool_memberships` | car/user/seat/order 引用、waiting_deployment/cancelled、创建时间；同车同人待部署成员唯一；订单只能生成一个成员；service_start/end 均为空 |
| `carpool_nodes` | 稳定 node_id、唯一 car_id、登记信息、registered 状态；阶段 1 只登记，不存真实凭证、不做远程连接、健康探测或激活 |
| `carpool_events` | event_id、车辆版本、事件类型、actor、时间与必要的非敏感关联 ID；同车辆版本/事件唯一；车辆变更与事件同事务落库 |

金额用整数最小货币单位，不用浮点金额参与比较。测试第一版建议只允许 CNY（分），显示时再格式化。价格必须大于 0，天数与交付时限为正整数，招募截止时间晚于数据库当前时间；这些字段必须由管理员填写，不擅自设定真实售价。

车辆发布时冻结容量、价格、币种、周期、交付和退款规则；如需修改，取消后新建车辆，不在已有订单上改变购买条件。订单保留当时快照。车辆不物理删除，有历史订单的用户关联也不得静默级联删除。

座位、订单、成员的同车同人关系在事务写入时校验，能用联合外键/唯一约束表达的同时交给数据库约束；不能只依赖前端校验。历史订单引用座位，不妨碍过期后该座位被新订单使用。

## 5. 状态与计数

### 车辆

`draft → recruiting → awaiting_deployment`。

- draft：仅管理员可见；发布前校验配置和固定座位数量。
- recruiting：截止时间前可占位；**只有 confirmed 数等于容量才满员**。
- awaiting_deployment：记录 full_at 和由交付时限计算的预计交付截止；不代表服务器已部署或资格已生效。
- recruiting 截止时未满：转 `closed_unfilled`，释放 pending 占位，取消测试成员；不进入部署。
- draft/recruiting/awaiting_deployment 可由管理员转 `cancelled`，同事务终结测试订单和成员、释放座位、记录原因；取消不可重新开放。不伪造真实退款记录。
- 阶段 1 不提供 deploying/active/expired/suspended 的人工捷径；实际开通与服务到期留待后续阶段。

### 座位与测试订单

`available → held → confirmed`；pending 订单过期或用户主动取消后 `held → available`。用户不得自行取消已 confirmed 的成员或转给其他用户；复杂退座、补位留待后续设计。

页面分开展示：已确认（测试）、占位中、可用座位。三者合计等于容量。有效占位按数据库时钟判定，不把过期但尚未清理的行算作占位；列表带服务端时间用于倒计时，倒计时不是最终授权依据。

满员事件唯一落库，同时可由管理员待部署列表查到。阶段 1 不启动邮件发送 worker；事件存在不等于邮件已发送。

## 6. 并发、幂等与恢复

所有座位相关写入统一锁顺序：先车辆行，再座位，再订单/成员。容量最多 4，每车串行事务比引入 Redis 分布式锁更容易验证；不同车辆不互相锁定。

1. 占位：认证用户 ID 来自 JWT，不信任 body 中 user_id；读取幂等结果后锁车、校验招募状态及截止时间、清理该车过期占位、检查同人有效座位、分配最低可用序号，创建测试订单并占位，同事务提交。
2. 占位截止：`min(数据库当前时间 + 10 分钟, 招募截止时间)`。每次写入获得车辆锁后重新取数据库当前时间，避免锁等待使请求使用陈旧时间。
3. 幂等：同用户、同键、同请求返回原订单；同键不同请求返回 409。键被过期订单占用时仍返回该订单，不自动变成新占位，用户需使用新键。不同键也不能绕过同人同车唯一约束。
4. 测试确认：锁车与订单，校验 mode、订单 pending、未过期、座位仍归该订单，再将座位/订单确认并创建 waiting_deployment 成员；满足满员条件时更新车辆并写唯一 full 事件。
5. 同一确认重放返回原结果，不重复成员/事件。到期后、座位已转给他人或车辆关闭后的确认返回 409，不抢回座位、不产生节点权益。无真实扣款，因此阶段 1 不模拟真实退款完成状态。
6. 释放：定时到期扫描与用户占位/确认用同一事务逻辑；重复处理无副作用。服务重启后扫描未完成过期记录，正确性不依赖 Redis、进程内定时器或前端倒计时。
7. 确认与过期、取消与确认竞争必须二选一；不能出现 confirmed 订单无对应成员、空闲座位仍有有效成员或取消后又满员的组合。

## 7. API 与权限契约

阶段 1 大厅要求登录；“公开列表”指面向普通登录用户的列表，并非匿名开放。列表只返回车辆信息和聚合人数，不返回成员 ID、邮箱、OIDC subject、订单或节点凭证。

| 接口建议 | 权限与行为 |
| --- | --- |
| `GET /api/v1/carpool/cars`、`GET /api/v1/carpool/cars/:id` | 已登录用户；只显示已发布车辆，分页与状态筛选 |
| `POST /api/v1/carpool/cars/:id/reservations` | 已登录用户；`Idempotency-Key` 必需；不接受金额、user_id、status 或 node_id |
| `GET /api/v1/carpool/orders/:id`、`POST .../:id/cancel` | 仅订单本人；他人资源 404；只允许取消 pending |
| `GET /api/v1/carpool/mine` | 只返回当前用户的占位、订单及成员状态；未开通不返回可用节点入口 |
| `GET/POST /api/v1/admin/carpool/cars`、`GET/PATCH .../:id` | 原管理员鉴权与审计；PATCH 仅 draft，不允许通过 body 越级改状态 |
| `POST .../:id/publish`、`POST .../:id/cancel`、`GET .../:id/members` | 管理员状态命令与成员查看；取消要求原因，涉及已确认测试成员需明确确认 |
| `POST /api/v1/admin/carpool/nodes` | 管理员仅登记节点；不接受凭证，不触发远程请求、不宣称节点可用 |

feature off 或运行在节点 B 时上述业务接口不注册（404）。401 表示未登录、403 表示非管理员、404 隐藏他人资源、409 表示座位/状态/幂等冲突、400 表示参数错误、503 表示依赖故障。数据库异常不得返回占位成功。

沿用 `routes/user.go` 中 JWT、后台模式 guard、限流与审计；管理员沿用 `routes/admin.go` 的 AdminAuth、审计和合规 guard，不为演示绕过合规确认。测试确认 CLI 不代替操作者接受任何合规声明。
