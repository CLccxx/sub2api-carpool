# 阶段 2：人工入车与站外收款登记设计

日期：2026-09-18（Asia/Shanghai）

状态：用户已确认「管理员直接加人、用户不自助占位、站外收款人工登记」的首版范围。本文是该范围的书面设计，具体规则待用户复核；尚未编写阶段 2 业务代码或执行验收。

## 1. 目标与范围

用户自行在主站 A 注册，与管理员在站外沟通、付款。管理员在自己的收款账户核实到账后，在主站选定用户和车辆，登记收款并确认成员。满员后进入待部署，管理员再准备服务器和上游账号。

本阶段只做到「人工确认收款 -> 正式成员 -> 满员待部署」以及未开通服务的退出、人工退款登记，不授予节点权限、不开始服务计时。

采用独立的人工确认来源，不调用现有充值、订阅或测试订单履约。未来在线支付通过另一个可信确认来源进入座位与成员流程，不把本次人工记录改写成渠道验签结果。

### 路线选择

| 路线 | 代价 | 决策 |
| --- | --- | --- |
| 管理员直接添加已注册用户 | 每笔人工核账，但业务路径最短 | 用户已选择 |
| 用户先提交报名，再由管理员审核 | 增加待审核队列、超时及撤回规则 | 首版不做 |
| 官方支付或第三方发卡平台 | 依赖商户准入、接口、结算及退款能力 | 延期，另行确认后接入 |

不做：付款二维码、支付链接、回调、自动查账、截图识别、代用户转账、钱包充值、押金/分期/折扣、部分退款、转座、自动补位、节点自动部署或采购。本期不以 SMTP 为依赖，满员状态和后台列表是持久化的工作清单；邮件发送留后续通知任务实现。

## 2. 业务规则

### 2.1 人工确认入车

1. 管理员从已注册用户中搜索并选择账号，确认邮箱和稳定 user_id，不能只按昵称确认身份，也不替用户创建账号或设置密码。
2. 只能向人工模式、已发布、招募未截止且有可用座位的车辆添加有效用户。
3. 记录渠道（支付宝或微信）、实际收款金额、收款时间和可选交易参考号、管理员备注。金额使用整数分；首版要求等于该车发布时冻结的单席价格，币种为 CNY。
4. 收款时间由管理员填写，不得晚于数据库当前时间；系统另记不可修改的登记时间及操作者。渠道名称仅代表管理员登记的站外收款方式，不代表平台已核验渠道交易。
5. 管理员必须明确确认已自行核实到账。浏览器勾选仅是确认动作，后端仍须做管理员鉴权、校验及审计；普通用户无确认入口。
6. 座位、正式订单、收款登记、成员和事件在同一事务内写入，直接产生 confirmed 座位和 waiting_deployment 成员，不经过十分钟 held 状态。
7. 同人同车最多一个有效座位，可参加不同车辆；多个管理员争抢最后一席时只允许一个成功。
8. 人数达到容量时原子进入 awaiting_deployment，写入满员时间和交付截止时间，停止加人。服务起止时间仍为空。

主站不能自动发现站外转账。管理员应先确认余位再安排收款；若用户已转款但录入时车辆满员或关闭，平台必须明确拒绝入车，不宣称已经退钱。未成功入车的站外款项由管理员另行核对和退还，本期不充当完整外部流水账。

### 2.2 幂等与收款凭据

- 每次人工入车使用独立 Idempotency-Key。同一操作者、同一动作、同键同请求返回同一订单及其当前状态；同键不同内容冲突。已退出的旧请求重放不得恢复成员。响应丢失后必须使用原键核对/重试，不产生第二个成员。
- 已填写的交易参考号按渠道规范化后去重，不能重复用于其他登记，包括已经退出或退款的历史登记；首版同一笔外部交易只登记一个座位，不支持合并付款分摊。未填写参考号时不声称能自动识别重复到账。
- 收款记录不可直接覆盖修改。误选用户或误录信息走有原因的退出/退款处理，并保留原记录，不删除历史掩盖错误。
- 参考号和内部备注仅供管理员查看。不给普通用户返回他人的身份、交易参考号或内部备注；不保存付款截图、银行卡号、账号密码或支付凭证密钥。

### 2.3 退出、取消与退款

| 操作 | 成员与座位 | 收款与退款 |
| --- | --- | --- |
| 招募中移除一名成员 | 成员及业务订单取消，释放该席位；车辆仍在原截止时间内招募 | 保留收款，生成 pending 人工退款记录 |
| 满员待部署时移除成员 | 成员取消、释放座位；车辆转 needs_review（待处理），停止加人和交付，不自动补位 | 为退出成员生成 pending，其他成员记录不变 |
| 管理员取消整车 | 所有有效成员取消、释放座位，车辆 cancelled | 为每个尚未退款的人工订单补建 pending |
| 招募到期仍未满员 | 车辆 closed_unfilled，成员取消、释放座位 | 同事务为对应人工订单补建 pending |
| 管理员确认已在站外退款 | 不恢复成员或车辆 | pending -> refunded，记录退款时间、金额、操作者及可选参考号 |

- 所有移除/取消必须填写原因；涉及成员时必须明确二次确认。重复命令不能重复生成退款记录。
- 本期尚未开通服务，退出按本设计做全额退款登记。人工车辆的退款规则使用服务端固定文本「未开通服务前退出、招募失败或车辆取消，全额退款，由管理员在站外办理并登记」，创建/编辑时不能自定义冲突规则；发布时冻结该文本。测试车保留原规则字段行为。
- pending 不代表钱已经退回；只有管理员在站外完成退款并确认，才显示「已人工退款」。系统不调用任何退款渠道。
- 首版没有 needs_review 自动恢复或补位按钮。管理员核对后可取消该车，按原记录处理退款；更复杂的恢复招募、替补和转座另行设计。
- 同一用户在同车还有待退款记录时禁止再次添加，避免旧款未清又登记新款；退款完成后仍须满足车辆可招募条件，使用新的确认键和收款记录。
- 到期清理、人工入车、退车和取消整车使用相同的车辆锁顺序。到期清理不把人工订单标成 refunded，也不删除收款信息。
- worker 尚未处理到期时，读取层仍拒绝加人并显示招募已关闭/待退款；该展示不代替持久化退款任务，worker 重启必须补齐处理。
- 服务已开通后的按比例退款、撤销节点权限由后续阶段设计；本期不提供已开通状态或开通命令。

## 3. 数据与模块边界

沿用 Go/Gin/PostgreSQL/Vue、现有拼车领域目录和独立迁移器。新增迁移，不修改已执行的 001、002 文件及其校验和，不改上游余额、订阅、调度和转发逻辑。

### 3.1 模式隔离

- 增加默认关闭的人工入车配置，与测试订单配置互斥；主站与节点模式互斥继续保留。
- 车辆新增服务端决定的 enrollment_mode（test/manual），创建后不可切换。已有车辆与订单保持 test，不自动转成正式收款或真实成员。
- 新建人工车辆、确认成员只在人工模式开启时允许；测试 CLI 只能操作测试车的测试订单，不能确认人工订单。
- 人工模式下用户大厅及「我的车」只展示人工模式数据，直接访问测试资源亦不能混入正式流程。管理员可以查询历史测试数据，但不得在测试车辆上登记正式收款。
- 关闭人工入车开关时禁止新增登记；已有正式记录仍可查询，管理员仍能退出、取消及登记退款。结果未知的新增请求可通过管理员只读订单查询核对，不能因开关关闭而无法判断此前是否成功。关闭主站或运行 B 节点时不注册主站业务路由。
- 用户自助预约不只隐藏按钮：人工模式中，旧预约入口必须拒绝请求。用户不能通过旧取消订单接口取消正式成员或标记退款。

### 3.2 持久化结构

| 对象 | 设计 |
| --- | --- |
| carpool_cars | 增加 enrollment_mode 和 needs_review 状态，保留原固定容量及发布快照 |
| carpool_orders | 扩展 mode=manual；人工订单直接 confirmed，无支付占位截止，expires_at 可空；test pending 仍必须有有效截止 |
| 人工收款记录 | 与订单一对一；金额、币种、渠道、收款时间、登记人、登记时间、参考号及内部备注；保留不可变原记录 |
| 人工退款记录 | 与人工订单一对一；pending/refunded、金额、原因、申请和完成时间、操作者；状态迁移具备幂等保护 |
| 人工命令幂等记录 | 操作者、动作、键、请求摘要、结果关联 ID，唯一约束；与业务变更同事务 |
| carpool_memberships / seats / events | 复用现有所有权和唯一约束；记录人工来源和审计事件，不包含原始敏感收款备注 |

关键一致性：人工订单与人工车辆匹配；一订单一收款、一成员、一退款任务；成员所属用户与座位/订单一致；金额与冻结价格一致。余额、订阅、B 节点授权和服务起止时间不变。

现有 carTransaction 允许业务拒绝时提交到期清理。人工写命令需要在到期清理后用事务保存点隔离命令写入：业务拒绝回滚该命令的全部写入，数据库错误回滚整个事务，防止只写入收款却没有成员。不得依赖「返回冲突自然回滚」这一错误假设。

### 3.3 接口职责

- 用户选择复用现有 `/api/v1/admin/users` 分页搜索，提交稳定 user_id；执行时重新检查用户状态，不信任页面缓存。
- 人工入车、成员退出、退款确认新增管理员命令 API；沿用 AdminAuth、合规 guard、限流和审计，不增加普通用户或公网确认入口。
- 管理员成员详情返回明确的身份展示字段及人工收款/退款状态，不让前端自行推算是否到账或退款。
- 复用车辆列表和「我的车」，增加本人可见的收款方式、金额、登记状态与退款状态。公开车辆列表只返回汇总席位，不公开成员邮箱。
- 未登录 401、普通用户访问管理操作 403、他人资源 404、模式/容量/状态/幂等冲突 409；无合法业务记录时不能返回成功。
- 对敏感备注和交易参考号做日志审查：应用日志和通用请求审计不得无差别记录这些字段；领域审计仅记录必要关联 ID 和动作。

## 4. 页面行为

### 管理员车辆页

- 沿用现有列表、成员弹窗和确认组件，不重做整站。
- 招募中的人工车辆增加「添加成员」。先搜索并明确选择用户，再显示只读价格和收款表单、到账确认；二次确认显示车辆、邮箱、用户 ID、金额。
- 搜索输入改变立即清除旧用户选择，忽略过时响应；提交期间不能换人、换车或重复点击。请求结果未知时保留原幂等键，支持核对和安全重试。
- 成员列表显示用户身份、席位、登记人/时间、收款与退款状态；提供有原因的移除和人工退款确认。
- 保留待部署筛选，增加待处理与待退款入口。退款入口覆盖已取消和招募关闭车辆，不能因不再是有效成员而隐藏欠退记录。

### 拼车大厅

- 保留已验收的紧凑席位目录、响应式布局、筛选和详情。
- 人工模式不展示测试预约、付款按钮或支付倒计时。以「联系管理员」展示已配置的站点 `contact_info`，按纯文本安全呈现，不嵌入支付页面或收款码。
- 未配置联系方式时不创建虚假联系按钮；管理员侧提示补充现有站点联系方式。
- 满员、已截止、已取消或 needs_review 车辆不显示可报名暗示。退出导致的 needs_review 明确显示「待处理」，不能继续标为满员。

### 我的车

- 管理员确认后显示对应车辆、席位、人工确认收款及待部署状态；退出后保留历史及待退款/已人工退款状态。
- 没有用户自助占位、取消正式成员或自称已付款的入口。
- 未开通时无节点入口，服务起止时间保持为空；不能因用户已付钱就显示可用 API Key 或服务已开始。
- 保留双语、加载/空态、错误/重试、后台刷新与桌面/移动适配。

## 5. 验收与实施拆分

### 2A：模型、事务与权限 API

先补失败测试，再实现增量迁移、人工确认、退出、退款登记、模式隔离、到期任务及管理员接口。使用真实 PostgreSQL 验证事务和并发，不以 mock 代替约束验证。

### 2B：管理页面与用户页面联调

实现成员搜索/收款登记、退出/退款、联系管理员和「我的车」状态，覆盖浏览器桌面与移动流程；复跑阶段 0 的 A/B 权限隔离，确认人工入车仍不自动授权节点。

| 验收场景 | 通过标准 |
| --- | --- |
| 2/3/4 座人工入车 | 恰好容纳对应人数；只有管理员能登记 |
| 最后一席并发、同人重复、同键重放 | 不超卖、不重复收款记录/成员，同键不同内容拒绝 |
| 操作已提交但响应丢失 | 原键可恢复结果，不生成第二条订单 |
| 金额/用户/车辆非法，停用用户 | 拒绝，不残留部分人工命令写入 |
| 参考号重复、跨渠道及空参考号 | 按约定去重，无参考号时不声称已自动核账 |
| 数据库故障、操作中业务冲突 | 原子回滚；只有合法到期清理可独立提交 |
| 截止与入车竞争、重复扫描、进程重启 | 截止后不加人，退出与退款任务可恢复且不重复 |
| 退车、整车取消、未成团 | 收款记录保留，待退款不伪装成退款完成 |
| 满员后退出 | 进入 needs_review，阻断加人和交付，不重置交付承诺 |
| 确认人工退款、重复确认 | 仅一次状态迁移，金额为原收款全额，保留操作者和时间 |
| 模式开关与老数据升级 | 旧测试数据不变；测试/人工互不履约；关新增仍可处理已有退款 |
| 用户越权与字段隐私 | 不能搜索他人、确认付款、看内部备注或修改退款状态 |
| 桌面/手机、长文本/双语 | 不溢出，搜索旧响应不改选中账号，流程和状态一致 |
| A/B 回归与资金副作用 | 无自动 B 授权、余额/订阅变更、外部支付或邮件发送 |

完成标准：2A、2B 均有独立验收证据，操作可审计，正式人工数据与测试数据隔离。此后继续阶段 3 节点授权和阶段 4 开通交付；商户支付接入不再是推进这两阶段的前置条件。
