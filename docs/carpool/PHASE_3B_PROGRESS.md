## Code at the First 3B Checkpoint

- `005_managed_members.sql`: new main-subject table, immutable node/main/car/group/instance binding, and managed members with version/digest/status/service/lease fields. Existing released/prerequisite migrations 001-003 were not edited. The new 005 was refined only against disposable tests before release to make NULL/digest checks explicit.
- `managed_members.go`: validates exact target and canonical subject UUID; atomically creates a fixed-role internal user and mapping using advisory locking. Zero balance, concurrency 1, restricted public groups, no balance emails, unusable password hash and `.invalid` email. No UserRepository signup/default-credit/subscription/email-identity hooks. Retry returns the same user, deleted identity is not reassigned.
- `managed_grants.go`: versioned grant application with same-version digest replay, stale/conflicting rejection, UTC microsecond normalization, authoritative DB time and maximum 15-minute lease bounded by service end. Inactive states have no service dates. Model gate reads fresh member/user/expiry state on every request and never falls back to OIDC.
- `NodeControl` persists and checks the fixed target binding on restart, including group ID. Existing OIDC grants still prevent managed startup.
- `AuthService.CheckNodeUser` and `CheckNodeIdentity` reject all managed member web sessions even if the model gate allows that member. Separate admin recovery remains. `APIKeyService` continues using the model gate rather than the web-session policy.
- `control_subjects.go` now assigns a stable UUID to each active A user. Concurrent calls and user deletion do not reassign subjects. Full upstream-schema provisioning checks verify no email identity or default subscription was created.
- Typed `ControlClient.Provision` / `ApplyGrant` and B member/grant routes are wired. Every command includes exact main/node/car/instance headers and canonical subject IDs. Unknown body fields and wrong bindings are rejected.
- Native `APIKeyRepository.Create` and `GetByID` now honor the ent transaction in context. `Update` already honored it and was preserved. An external-transaction regression verifies creation and absolute expiry roll back together.
- `006_managed_key_commands.sql` and `CarpoolManagedKeys` implement B create/replay/rename/enable/disable/delete. The member/user/key locks, native APIKeyService operations, service-end expiry and command ID/hash are in one ent transaction. No secret response is stored in command metadata. Deleted keys retain a command tombstone; disabled/deleted/expired keys are not recreated or exposed by replay. Create and enable recheck the lease and key expiry with database time before commit; cache invalidation runs again after commit, with an independent two-second context so a disconnected caller cannot cancel it.
- B key handlers, providers and generated Wire injection are present. Mutation responses omit the full key; all delegated handler responses use no-store. Authentication, compliance and strict body restrictions remain in effect. B now advertises `delegated-keys` and `bound-admin-reads` alongside its earlier capabilities.
- Typed A-to-B key commands preserve the operation ID and use fixed routes. Known conflict/not-found/member-denied errors are mapped to local error classes without retaining the remote message or metadata.
- `control_queries.go` implements typed native admin key-list/usage/stats clients. They require a fresh matching node identity and `bound-admin-reads`, fix user/group filters internally, cap pages at 100 and date ranges at 31 inclusive UTC days, and return whitelisted fields. Lists omit key secrets. Mismatched owners/groups and malformed responses fail rather than return an empty success. Native delegated reads are also protected by `EnforceControlTarget` inside the authenticated B admin route group, closing the gap between preflight and the actual read.
- `007_main_service_windows.sql` adds A car/member service states and bounded date pairs without adding an activation command. `main_service_window.go` guards old whole-car cancellation and per-order withdrawal/refund, including replay, against served records. Pre-service cancelled orders can still be refunded after other members start service. New statuses are accepted by the existing list filters. Active transitions only occur in the isolated `activateMainFixture` test helper.
- `008_main_node_members_and_keys.sql` persists A's pinned remote user/group/instance mapping and metadata-only create journal. `PrepareMember` stores a pending mapping before calling B and checks generation/identity on completion; it never calls ApplyGrant. `CreateMemberKey` commits actor/car/membership/subject/hash/stable downstream operation ID before HTTP, recovers lost responses with that same ID, and verifies current eligibility/generation/database time again before storing the downstream key ID or returning a secret.
- `009_main_key_barriers.sql` records metadata-only disable/delete barriers before sending a mutation, suppressing a create response already in flight. Confirmed deletion is not claimed on remote errors; retry still calls B. The barrier suppresses secret recovery even while deletion is uncertain. Explicit enable can clear a disabled barrier only after a valid node response and fresh A eligibility check; a deleted barrier is not cleared. No plaintext key is stored in either A table.
- `control_member_operations.go` supplies A rename/enable/disable/delete plus scoped reads, resolving every node/user/group from A's authenticated actor and membership. Reads also recheck actor and pinned connection before returning. `carpool_member_control.go` and user routes now expose the six specified key/usage endpoints; no client-supplied user/group/URL/actor is accepted. Responses use no-store; key lists and mutations omit full secrets; usage inherits the existing heavy limiter. **Automatic mapping/grant synchronization and the member-console status endpoint/UI are still absent.**

### Durable Synchronization Checkpoint

- `010_control_sync.sql` adds a durable desired-grant/outbox row per node/subject. It stores canonical payload hashes, monotonically increasing versions, connection generation, stable operation IDs, acknowledgement metadata, retry times and 45-second claim leases. It contains no plaintext API keys or response bodies. Migrations 001-009 were not changed in this checkpoint.
- `control_sync_publish.go` publishes from the same car transaction as enrollment/withdrawal/cancellation. `MainService` installs its optional publisher only when the control store is constructed. An outbox failure rolls back the business change. Prepared connections or mappings never activate a service; only authoritative active service windows can project an active grant. Those windows remain test-only in phase 3.
- `control_jobs.go` claims work with PostgreSQL `SKIP LOCKED`, one current claim per node. It prioritizes revoked/paused work, revalidates before provisioning and before sending a grant, and accepts completion only for the current claim, operation and generation. Unknown remote outcomes retain replayable work. Retries use 2/5/15/30/60 seconds with 20% jitter, stopping after six failed attempts; auth, compliance, credential, protocol, identity, grant-window and version errors require operator action immediately.
- `CarpoolControlWorker` starts reconciliation immediately and every 60 seconds, with two bounded delivery lanes and cancellation/join on shutdown. Wire includes its lifecycle. Generic user disable/delete is detected by reconciliation. A recovered claim does not change the downstream operation or payload; an expired owner cannot acknowledge its replacement.
- Active leases are capped at 15 minutes and service end, renewed five minutes before expiry. A specific `CARPOOL_GRANT_WINDOW` error reports rejected lease/service windows without copying remote messages or silently extending a window.
- New authenticated member endpoint: `GET /api/v1/carpool/cars/:id/console`. New administrator endpoints: `GET /api/v1/admin/carpool/cars/:id/sync` and `POST /api/v1/admin/carpool/cars/:id/sync/retry`. Retry inherits step-up; an unavailable connection cannot falsely report queued work. All three responses are no-store. Status distinguishes unactivated/prepared, synchronization, errors, effective service and historical read/cleanup ability; it exposes no remote user IDs or credentials.
