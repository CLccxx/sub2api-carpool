# 拼车需求基线与阶段 4 收敛方案

日期：2026-09-22；最后更新：2026-09-23（Asia/Shanghai）

状态：本文件保留实施前需求基线及当时的代码差距。2026-09-23 用户已确认不要求相同邮箱密码登录 B，继续采用只登录 A 的内部用户映射。随后阶段 4A-D 已按此方向完成本地开发验收，实际进度以 `PHASE_4_EXECUTION_PLAN.md` 和各阶段 RESULTS 为准；下文“当前”“尚未实现”等属于实施前快照，不覆盖这些验收记录。没有生产部署、购买、提交或推送。

## 1. 产品目标

只做「A 的拼车管理和统一用户入口 + B 原生 sub2api 服务」，不重新开发计费系统。

- 拼车页面嵌入 A 的 sub2api，B 不开放拼车大厅。乘客在 A 注册、登录，正常使用无需再次登录 B。
- 首版站外微信收款，管理员核实后把 A 的已有用户加入指定车辆；不做在线支付，不开放用户自助占位。
- 管理员可同时发布多辆 2 人、3 人、4 人车。大厅展示车辆状态和已加入人数，例如「拼车中，1/4」是已加入 1 人，而不是剩余 1 位。
- 满员后由管理员自行购买服务器 B、部署 sub2api，再在 B 通过 OAuth 授权本车使用的上游账号。该上游账号与乘客的本地用户是两类身份。
- 每车绑定自己的 B 地址、管理员 API Key 及上游账号；若 B 上存在多个账号，需明确选择本车账号，不能任意取第一个。管理员 Key 只在 A 后端保存和使用。
- 「一键同步/初始化」完成本车用户映射、原生订阅分组、上游账号与组的关联、每位成员的订阅分配；失败可继续，不重复创建或意外续期。订阅初始化完成才交付使用，不因单纯入车/满员自动开始服务。
- 成员在 A 的「我的车」创建 B 上自己的 API Key，所属分组为本车分组，然后用客户端直接请求 B 的模型接口。
- A 展示 B 的本人使用记录、订阅、额度、重置时间及整车账号使用百分比。请求是否成功、计费和额度限制由 B 负责，A 不充当模型代理。

## 2. 三种金额分别处理

`N` 是该车规定人数（2、3 或 4），不是当前已经报名的人数；`T` 是绑定上游账号本周有效的预计总费用。

| 金额 | 最新需求 | 4 人示例 |
| --- | --- | --- |
| 拼车人民币售价 | 管理员可修改整车总价，默认 1400 元；每人价格 = 整车总价 / N | 1400 / 4 = 350 元/人 |
| 首次/新周无有效估算时的个人周额度 | 1800 / N，按 B 的 USD 计费额度填写 | 1800 / 4 = 450 美元/周 |
| 有有效预计总费用后的个人周额度 | (T - 100) / N，更新同一分组的周限额 | T=2000 时为 475 美元/周 |

用户本次明确恢复「预计总费用先减 100」：之前文档中的 `T / N` 和 2000 对应 500 已作废。初始 1800 按用户明确公式直接除以人数，不再先减 100。人民币售价、1800 兜底额度和 100 预留额度互不混用。

建议首版每小时更新一次有效周限额，并保留管理员手动刷新；暂不同时实现每次估算变动实时推送。只改限额，不重置已用，不重建组，不重新分配订阅。上限下降后能否继续请求交给 B 的原生规则。

金额处理建议：总价设置提供默认值并随车保存，按分精度计算人均价；1400 / 3 显示 466.67 元，金额精度可能造成一分钱的总额差异。配置调整不追改已经登记的真实收款和订单快照。当前代码仅允许草稿改价，已发布车辆的改价入口不能假定已支持。

无效、陈旧或读取失败的估算不覆盖最近成功限额；`T <= 100` 等导致非正额度的结果标记异常，不盲目写 0 或清空周限额，以免触发 B 的不限额语义。确认新周且没有有效估算时再用 1800，不把接口错误当成新周。

## 3. B 的原生配置

- 创建「4 人车分组」（其他人数同理），计费类型为订阅，只设置周限额，不增加日/月/五小时限制。
- 把本车的 OAuth 上游账号关联到该分组；每名乘客在 B 有独立普通用户及该组的独立订阅。只建立用户和组而不分配订阅，不能完成交付。
- 个人 Key 绑定本车组。因为每车只有一个目标组，A 可显示并默认选择该组，不必让用户从其他车辆/全站分组中挑选。
- 订阅时长沿用车辆已确认的服务时长；B 的订阅有效期、用户/Key 状态及周限额负责实际生效。自动化不能把失败或过期订阅通过重试意外变成续费。
- 保存稳定的 A 用户到 B 用户、车辆到节点/组/账号的对应关系，不能只靠相同邮箱或分组名称反复认领已有对象。

## 4. A 中的「我的车」

| 内容 | 来源/行为 |
| --- | --- |
| 本车 API 地址、个人 Key 列表及创建/管理 | B 的实际 Key 和操作结果；Key 属于本人并绑定本车组 |
| 使用记录逐条、日期筛选、分页、汇总 | B 的本人且属于本车范围的记录；时间、模型、Token 和费用均使用 B 数据 |
| 订阅列表/详情、总周额度、已用、剩余 | B 的原生订阅及进度；不在 A 另算用量账本 |
| 重置时间及倒计时 | B 账号管理中本车上游账号的总体周窗口，不采用个人首次使用时间 |
| 整车账号使用百分比、预计总费用 | B 本车绑定上游账号的用量窗口；不泄露 OAuth 凭据 |

A 只做页面展示、必要格式化、本人/本车数据隔离以及调用 B 的受控接口。B 的管理员接口结果必须裁剪为普通用户可见字段，不能原样转发管理员数据或让浏览器自选任意用户 ID。不要保存或伪造 B 登录会话来实现免登录。

B 读取失败就显示读取失败/旧数据时间，不把错误展示成零用量。模型客户端直连 B，B 的模型错误直接返回客户端。页面刷新失败、调额失败、重置待核实/执行中不增加请求暂停，不自行禁用 Key，也不代 B 放宽限额。管理员对车辆的真实退出/退款/停用操作仍需映射为 B 的用户/订阅/Key 状态变更，这与同步故障停流不同。

## 5. 周重置的最小规则

目标是账号换周时，本车各用户的原生订阅周已用同步归零；只重置周已用，不删除历史记录，不改收款，不延长订阅。

1. 以本车上游账号的总体周窗口为准。倒计时到期或观察到使用率从非零降到零可触发检查；不能把页面取整、缓存过期构造的 0% 或接口异常作为唯一清零证据。
2. 核实有效账号周期后执行一次整车周重置；不要求恰好采到 0%，新周已经有少量使用也应能识别。持续 0% 的未使用账号同样依据窗口时间处理。
3. 自动和管理员一键补同步共用已处理周期记录，同一周期重试不再清掉后来产生的新用量。防重复记录属于同步元数据，不是另一套用量账本。
4. 原生订阅自己的七天窗口不能与账号周窗口分别重置，需补齐最小周期对齐；仅改 A 倒计时、循环点击原生重置按钮不等于完成同步。
5. 重置和并发扣费都在 B 原生记录上处理，不暂停新请求、不等待全车请求排空。A 只展示 B 的实际结果；消费归属沿用 B 实际记账/重置执行时点，不建立精确到上游切换秒的另一套分摊算法。
6. 数据不可靠就标记同步异常并重试，不盲目清零；B 仍按已有实际状态审核请求。正常同步存在检测和执行延迟，不能保证全车在上游重置的同一秒页面同时显示 0。

建议由 B 负责账号周期检测和原生重置，A 提供结果展示及一键补同步；A 每小时提交分组调额。调度只需一个正常频率的后台检查，暂不扩展为每请求事件系统或复杂的全局控制平台。不得调用上游付费重置/购买接口。

## 7. 已确认的身份方式

2026-09-23 用户明确不要求直接打开 B 登录页，使用与 A 相同的邮箱和密码登录。

- 沿用阶段 3 的内部用户映射：B 上的普通用户承担原生订阅、Key 和记录归属，乘客仍只登录 A。
- 不复制 A 的密码或密码哈希，不保存明文密码，不创建成员 B 登录会话，不新增 SSO 系统。
- B 管理员可识别这些用户的车辆及 A 成员对应关系；这属于显示标识，不改变认证方式。

因此阶段 3 的身份主方向不需要返工；需要调整的是初始化配置和额外授权租约，而不是重做注册登录。

## 8. 建议收简后的开发方向

1. 保留大厅、人工入车、站外收款记录、连接凭证保护、用户映射、Key 管理和原生使用记录查询，不推倒重做。
2. B 优先复用原生管理员 API 和订阅服务，只为缺失的本人 Key 委托/周期同步保留必要扩展。当前阶段 3 依赖定制 `/carpool-control/v1/*`，不是任意未修改的 B 填 Key 即可使用；部署方案需明确固定兼容版本并尽量自动生成技术配置。
3. 不继续叠加 A 的额度账本、独立计费/限流、复杂请求暂停或用户不可见的多套周期。建议调整现有短租约门禁，使 B 调用不因 A 续租中断而额外失败；到期、额度和撤销转为 B 原生订阅及状态生效。不能直接删除权限代码，必须先覆盖未开通、到期、撤销及跨车隔离回归。
4. 直接进入阶段 4，将对阶段 1-3 的必要修改纳入阶段 4 的对应子阶段；不重新执行一轮 1-3，也不先做一轮脱离新订阅功能的权限重构。建议按下表推进，每个子阶段开始前再形成具体实施步骤。

| 子阶段 | 交付范围 | 与旧代码的关系/验收边界 |
| --- | --- | --- |
| 4A：价格与人数口径 | 默认整车总价 1400、后台可配置、人均计算；大厅显示已加入/总人数 | 小改阶段 1/2；历史车辆、订单和实际收款金额不被新默认值追改；验证 2/3/4 人、金额精度及人工入车回归 |
| 4B：一键原生订阅开通 | 简化 B 连接配置，按依赖顺序建组、关联上游账号、预配成员、分配订阅、确认开通；在此阶段替换多余短租约依赖 | 扩展阶段 3，不重做身份/Key/用量；先证明 B 原生未开通拒绝、到期、撤销、组隔离有效，再切换门禁；失败重试不重复创建或续期 |
| 4C：展示及额度自动化 | 补「我的车」原生订阅/额度/账号窗口；每小时 `(T - 100) / N` 调额；账号周期对齐、自动/一键周重置 | 复用既有使用记录；验证 450→475不重置已用、周期只重置一次、A 不新增停流及所有展示以 B 为准 |
| 4D：完整联调与交付 | 人工入车→满员→初始化→开通→创建 Key→直连 B→查记录→调额/换周→到期，提供固定版本部署说明 | 重跑受影响阶段 1-3 回归和新链路；验证多车隔离、断网重试、A 不可达及 B 原生限制。生产购买/凭据/部署仍另行授权 |

关键顺序：4A 不移除阶段 3 门禁；4B 先补原生订阅及到期/撤销等效保障，再替换额外短租约。阶段 4 在 4D 整体联调通过前都不是可宣称已完成的生产交付。

验收重点：初始 450、T=2000 后 475且已用不变；账号换周一次清零、重试不重复清零；列表/订阅数值来自 B；一车失败不影响另一车；A 刷新或调额失败不新增停流；已开通 B 不因 A 短租约失效而停用（属于建议调整目标，当前代码尚不满足）。
